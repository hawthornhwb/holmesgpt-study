## 1 从一次故障调查理解安全问题

沿用教学场景：“checkout-api 为什么一直重启？”Agent 需要查询资源、事件和日志。这里讨论请求的处理方式，练习只做纸面推演。

| 情况 | 需要解决的问题 | 设计关注点 |
| --- | --- | --- |
| 模型试图读取不在授权范围内的命名空间 | 是否能访问这个资源 | Kubernetes RBAC 等实际权限边界 |
| 服务名等参数混入 Shell 特殊语法，改变原命令含义 | 输入是否改变了执行语义 | 参数处理与命令检查 |
| 调查途中提出修改资源等操作 | 是否符合当前策略，是否需要人决定 | 命令策略与人工审批 |

Prompt 可以指导模型选择行为，实际执行还需要程序检查和数据源权限约束。先用自己的话解释这三类问题，避免把所有安全机制都归结为“只读”或“加了黑名单”。

## 2 理解五个控制点的职责

| 控制点 | 负责什么 | 需要讲清的边界 |
| --- | --- | --- |
| Kubernetes RBAC | 限制实际身份可访问的资源、操作和范围 | 应用内获批也不能增加集群没有授予的权限 |
| Shell 参数处理 | 在参数化命令模板里引用参数，处理特定不可信输入 | 参数值处理与完整 Bash 命令检查是不同路径；模板写法也影响安全性 |
| Allow / Deny List 与命令检查 | 根据配置和命令结构作出允许、拒绝或需要审批的判断 | 需要分析复合命令等结构；应用策略本身不是操作系统沙箱 |
| 人工审批 | 对需要确认的具体调用取得人的决定 | 是否需要审批取决于工具和配置；拒绝时应返回明确结果 |
| Approval Token | 将待审批调用与调用 ID、工具名、参数摘要绑定，恢复时校验 | 保证内容绑定与签名校验；身份认证和完整的一次性防重放还需要其他机制 |

参数化 YAML 工具中，参数会经过引用等处理再进入模板；完整 Bash 工具面对的是一整条命令，需要命令策略判断。JSON Schema 描述参数类型，不能单独代替这两种执行检查。

当前 Helm 的 namespaceScopedRBAC 默认是 false；模板默认采用集群范围的角色，配置后可切换到安装命名空间范围。具体是否渲染以及实际拥有的权限，还取决于安装选项、ServiceAccount、角色绑定和自定义规则。面试中说明配置与检查依据即可。

这张职责表就是本模块的核心：权限控制访问能力，参数与命令检查控制执行输入，审批提供人的决定，Token 约束恢复时的调用内容。

## 3 推演决策与审批内容绑定

下面是概念路径，帮助理解各控制点的关系，具体入口的检查顺序以实现为准。

```text
模型提出工具名与参数
→ 程序按工具类型做参数处理、策略与审批判断
→ 允许：进入执行路径
→ 拒绝：返回明确错误
→ 需要审批：保存待审批调用并关联签名 Token
   → 收到人的决定，恢复时校验 Token 与调用内容
   → 同意且校验通过：恢复执行；拒绝或校验失败：返回拒绝结果
→ 访问 Kubernetes API 时仍受实际 RBAC 约束
```

结合四个教学情况复述：

- **查询日志符合当前允许策略。** 可进入执行路径，但如果实际身份缺少日志权限，Kubernetes API 仍可拒绝。
- **命令被当前策略拒绝。** 未经审批的 Bash 调用路径会返回拒绝错误；拒绝结果与待审批状态不同。
- **某项操作按当前配置需要审批。** 保留准确的工具、参数和调用 ID，展示具体操作，由人决定。普通命令调用缺少可用审批交互时，应说明调用被拒，不能说操作正在等待审批。
- **待审批请求恢复时，namespace 从 staging 被改成 prod。** 参数内容变化后，已有 Token 的参数摘要无法匹配，恢复应被拒。仅仅携带“已批准”标记不足以通过该检查。

Approval Token 使用签名，并校验有效期、调用 ID、工具名和规范化 JSON 参数的哈希。参数键顺序或空白变化可保持相同哈希，参数值变化应无法匹配。签名校验保护的是这个绑定；仅有 Token 不能证明审批人的身份，也不能据此宣称已经实现完整的单次使用控制。

至少讲出一项取舍：严格的策略降低误操作机会，也可能阻止合理调查；人工审批增加人的判断，但中断自动调查，并要求用户理解具体动作。需要结合工具用途和权限范围配置。

## 4 面试讲述与核心追问

先借助骨架讲一遍，再合上文档，用自己的话讲第二遍。简历表述是“分析并验证”这些机制，实际验证范围填写在文末。

> 工具安全从权限、参数和命令执行几个位置控制。Kubernetes RBAC 限制实际身份能访问哪些资源和操作；参数化 Shell 工具处理模板参数，完整 Bash 命令再根据策略和命令结构判断是否允许。需要人工确认的调用进入审批流程，返回具体操作给用户。恢复时用签名 Approval Token 校验调用 ID、工具名和参数摘要，防止待审批内容被改动。审批通过后仍受数据源权限限制。这样的分层设计让不同机制各自约束一类问题，但也有边界：命令策略不能等同于系统沙箱，Token 的内容绑定也不能代替身份认证或完整的防重放控制。

每个追问先回答 30–60 秒，卡住后只补当前问题。

| 核心追问 | 回答需要包含什么 |
| --- | --- |
| 为什么 Prompt 或“只读”说明不足以保证安全？ | 模型请求可能出错；程序检查与实际身份权限决定能否执行 |
| RBAC、参数处理、命令策略分别负责什么？ | 资源与操作权限、模板参数语义、完整命令的策略判断 |
| 为什么需要人工审批，拒绝和待审批有什么区别？ | 部分操作需要人的决定；拒绝返回结果，待审批需要有效交互与恢复路径 |
| Approval Token 为什么绑定调用 ID、工具名和参数？ | 防止待审批内容被替换；恢复时检查签名、有效期及内容匹配 |
| 审批通过后还有哪些限制，怎样验证这些机制？ | 数据源权限仍有效；Token 作用边界；正例、拒绝例和篡改例分别验证 |

答顺以后，再补两个深入问题：复合命令如何避免只检查第一段？签名密钥在重启后变化会怎样影响未完成审批？
