## 1 从一次故障调查理解安全问题

沿用已有 case：先发现准确 Pod，再通过 `fetch_pod_logs` 读取启动日志。原 case 没有强制审批或注入攻击；以下改变同一次调用的参数、权限与策略，做纸面推演，这些变化仍未运行。实测里真实出现过一次策略分支：6 条 `kubectl` 命令的片段未命中允许列表，工具返回 `requires approval`，而 pytest 入口没有审批交互，于是按拒绝处理，模型把 `-n` 参数移到命令末尾后重试成功。

| 情况 | 需要解决的问题 | 设计关注点 |
| --- | --- | --- |
| 读取 app-09 日志，实际身份没有 pods/log 权限 | 是否能访问这个资源 | Kubernetes API 返回 Forbidden；RBAC 决定权限 |
| Pod 名或 jq 参数混入 Shell 特殊语法 | 输入是否会改变执行语义 | 区分 Python 参数数组、YAML 模板与完整 Bash 命令 |
| 部署策略要求读取该日志也必须审批 | 怎样暂停并可靠恢复同一次操作 | 按配置返回待审批，恢复时核对具体调用内容 |

Prompt 可以指导模型选择行为，实际执行还需要程序检查和数据源权限约束。先用自己的话解释这三类问题，避免把所有安全机制都归结为“只读”或“加了黑名单”。

## 2 理解五个控制点的职责

| 控制点 | 负责什么 | 需要讲清的边界 |
| --- | --- | --- |
| Kubernetes RBAC | 限制实际身份可访问的资源、操作和范围 | 应用内获批也不能增加集群没有授予的权限 |
| Shell 参数处理 | 在参数化命令模板里引用参数，处理特定不可信输入 | 参数值处理与完整 Bash 命令检查是不同路径；模板写法也影响安全性 |
| Allow / Deny List 与命令检查 | 根据配置和命令结构作出允许、拒绝或需要审批的判断 | 需要分析复合命令等结构；应用策略本身不是操作系统沙箱 |
| 人工审批 | 对需要确认的具体调用取得人的决定 | 是否需要审批取决于工具和配置；拒绝时应返回明确结果 |
| Approval Token | 将待审批调用与调用 ID、工具名、参数摘要绑定，恢复时校验 | 保证内容绑定与签名校验；身份认证和完整的一次性防重放还需要其他机制 |

把本例的两个工具和完整 Bash 路径分开核对：

| 执行路径 | 参数如何使用 | 应观察的安全设计 |
| --- | --- | --- |
| Python `fetch_pod_logs` | `_fetch_kubectl_logs()` 构造参数数组交给 subprocess，默认不走 Shell 解释 | Shell 元字符不会自动变成第二条命令；仍要检查参数语义和资源权限 |
| YAML `kubernetes_jq_query` | 参数经过 sanitize 后插入脚本，脚本再引用变量 | 处理后的参数应放在正确的模板位置；错误的引号上下文会破坏引用保护 |
| 完整 Bash 工具 | 模型提供完整 command | 按配置与命令结构分析 Allow/Deny、复合命令和审批要求 |

JSON Schema 描述参数类型，不能单独代替这些执行检查。Bash 的 Allow/Deny 不能被说成每个工具统一经过的一道门。

该 eval 通过实际 kubectl 凭据访问测试集群，不能直接假定它使用 Helm 创建的 ServiceAccount。部署场景中，Helm 的 namespaceScopedRBAC 默认是 false；角色模板可按配置切换范围，是否渲染及实际权限还取决于安装选项、角色绑定和自定义规则。特别是本例的 `kubernetes_jq_query` 使用跨命名空间集合接口，即使 jq 最终只留 app-09 结果，也仍需该 API 读取权限。

这张职责表就是本模块的核心：权限控制访问能力，参数与命令检查控制执行输入，审批提供人的决定，Token 约束恢复时的调用内容。

## 3 推演决策与审批内容绑定

下面是概念路径，帮助理解各控制点的关系，具体入口的检查顺序以实现为准。

```text
模型提出工具名与参数
→ 程序按工具类型做参数处理、策略与审批判断
→ 允许：进入执行路径
→ 拒绝：返回明确错误
→ 需要审批：保存待审批调用并关联签名 Token
   → 收到人的决定，恢复时校验 Token 与调用内容
   → 同意且校验通过：恢复执行；拒绝或校验失败：返回拒绝结果
→ 访问 Kubernetes API 时仍受实际 RBAC 约束
```

继续使用同一个目标 Pod，结合四个情况复述：

- **fetch_pod_logs 无需审批。** 可以进入日志实现；实际身份缺少 `pods/log` 权限时，Kubernetes API 仍可拒绝，结论应说明证据未能取得。
- **改用完整 Bash，命令被当前策略拒绝。** 原始未获批调用返回拒绝错误。复合命令需检查各段，不能只因第一段是查日志就放过后面的动作。
- **配置 approval_required_tools: ["fetch_pod_logs"]。** 这是学习推演，不是原 case 配置。保留准确工具、参数和调用 ID，展示读取 app-09 某个 Pod 日志的请求，由人决定。当前入口没有可用审批交互时，普通调用会被拒。
- **待审批日志请求恢复时，namespace 从 app-09 被改成 prod。** 参数变化导致已有 Token 的哈希不匹配，恢复应被拒。仅携带“已批准”标记不足以通过检查。

Approval Token 使用签名，并校验有效期、调用 ID、工具名和规范化 JSON 参数的哈希。参数键顺序或空白变化可保持相同哈希，参数值变化应无法匹配。签名校验保护的是这个绑定；仅有 Token 不能证明审批人的身份，也不能据此宣称已经实现完整的单次使用控制。

至少讲出一项取舍：严格的策略降低误操作机会，也可能阻止合理调查；人工审批增加人的判断，但中断自动调查，并要求用户理解具体动作。需要结合工具用途和权限范围配置。

## 4 面试讲述与核心追问

先借助骨架讲一遍，再合上文档，用自己的话讲第二遍。简历表述是“分析并验证”这些机制，实际验证范围填写在文末。

> 在支付服务重启这个 case 中，读取日志受实际 Kubernetes 身份权限限制，审批通过也不能增加 pods/log 权限。参数安全则要看执行路径：默认 Python 日志工具构造参数数组，YAML 资源查询工具要处理 Shell 模板引用，完整 Bash 工具另做命令策略检查。如果配置要求日志读取也需审批，框架保存具体调用并签发 Token，恢复时校验签名、有效期、调用 ID、工具名和参数哈希。例如 namespace 从 app-09 改成 prod，原 Token 就无法匹配。设计难点是让不同控制点各自约束对应问题，同时说清 Token 的内容绑定、身份认证和单次使用控制之间的边界。

每个追问先回答 30–60 秒，卡住后只补当前问题。

| 核心追问 | 回答需要包含什么 |
| --- | --- |
| 为什么 Prompt 或“只读”说明不足以保证安全？ | 模型请求可能出错；程序检查与实际身份权限决定能否执行 |
| 本例的 Python 日志工具与 YAML 查询工具，安全路径一样吗？ | 参数数组与 Shell 模板引用的区别；完整 Bash 策略是另一条路径；API 权限仍有效 |
| 为什么需要人工审批，拒绝和待审批有什么区别？ | 部分操作需要人的决定；拒绝返回结果，待审批需要有效交互与恢复路径 |
| Approval Token 为什么绑定调用 ID、工具名和参数？ | 防止待审批内容被替换；恢复时检查签名、有效期及内容匹配 |
| 审批通过后还有哪些限制，怎样验证这些机制？ | 数据源权限仍有效；Token 作用边界；正例、拒绝例和篡改例分别验证 |

答顺以后，再补两个深入问题：复合命令如何避免只检查第一段？签名密钥在重启后变化会怎样影响未完成审批？

每次选一个问题，最多查看两段相关资料。10 分钟后仍卡住，就记录问题，通过中文解释或输入输出推演继续学习。

| 当前疑问 | 查哪一小段 | 查到什么即可停止 |
| --- | --- | --- |
| 当前 RBAC 范围在哪里配置？ | [Helm 配置](../../helm/holmes/values.yaml) 的 namespaceScopedRBAC；[角色模板](../../helm/holmes/templates/holmesgpt-service-account.yaml) 的 kind 与 rules | 区分 Role / ClusterRole，找到资源与 verbs |
| 本例参数是否经过 Shell？ | [kubernetes_logs.py](../../holmes/plugins/toolsets/kubernetes_logs.py) 的 _fetch_kubectl_logs()；[kubernetes.yaml](../../holmes/plugins/toolsets/kubernetes.yaml) 的 KIND / JQ_FILTER 赋值 | 一个是参数数组，一个需要模板和变量引用正确配合 |
| 完整命令怎样检查？ | [bash_toolset.py](../../holmes/plugins/toolsets/bash/bash_toolset.py) 的 requires_approval() / _invoke() | 区分允许、拒绝和待审批；它不是所有工具共享的检查路径 |
| Token 绑定什么，恢复在哪里校验？ | [approval_tokens.py](../../holmes/utils/approval_tokens.py) 的 mint_token()、verify_token()；[tool_calling_llm.py](../../holmes/core/tool_calling_llm.py) 的 _execute_tool_decisions() | 确认绑定字段，以及校验失败会导致拒绝 |

如果需要一条验证依据，可阅读 [Token 测试](../../tests/test_approval_tokens.py) 的篡改或过期断言，或者 [Bash 审批测试](../../tests/toolsets/bash/test_bash_approval_flow.py) 的允许、拒绝、待审批例子。模板测试证明渲染结果，Mock 测试证明对应程序分支；真实集群权限需要结合实际部署验证。测试执行按疑问选做。
