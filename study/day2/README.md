## 1 先写五句话 10 分钟

先照下面的结构填空，不查代码。不会的地方写“待补”，到第 5 项再修订。

1. 这个项目帮助谁解决什么问题？
2. 用户提问后，Agent 怎样查状态、事件和日志？
3. 工具为什么需要统一接入和调用？
4. 大量结果、安全边界和诊断质量分别怎样处理？
5. 我实际做过什么，有什么记录可以支撑？

项目机制的参考表述：

> 这个项目面向 Kubernetes 故障排查。用户给出问题后，模型结合工具说明选择查询操作，程序执行工具，再把结果交回模型，让它依据新证据决定下一步，最后输出诊断结论和建议。工具通过统一的接口接入，方便扩展不同数据源；上下文控制、安全检查和效果评估分别处理信息量、执行边界和诊断质量。

这段只是项目机制的介绍骨架。最后补上你真实完成的学习、验证或开发工作，例如已经核对过的消息流和补充的测试断言；不要把参考回答直接当作个人开发经历。

## 2 用实例理解五个概念 20 分钟

| 概念 | 一句话理解 | 放进你的项目 |
| --- | --- | --- |
| Tool | 一次可以执行的具体操作 | 查询某个服务的日志 |
| Toolset | 管理一组相关工具及配置、前置条件 | Kubernetes 工具集里放状态、事件、日志查询 |
| Schema | 告诉模型工具叫什么、何时用、参数怎么填 | 日志工具要求命名空间、服务名和数量上限 |
| Skill | 可复用的操作指导，可以带脚本和参考资料 | 你的开关归因 Skill 指导如何收集并交叉验证证据 |
| MCP | 让客户端和服务端按共同协议发现、调用工具等能力 | 可以通过 MCP 服务提供日志或变更查询工具 |

Skill 的定义参考 [Anthropic 官方说明](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)，MCP 的工具发现和调用参考 [MCP 官方工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。这两页今天无需全文阅读。

把它们连起来：一个归因 Skill 可以指导 Agent 使用多个工具收集证据，其中部分工具通过 MCP 接入。具体怎样实现，以你实习中的实际做法为准。HolmesGPT 的 Toolset 是该框架的组织方式，工具接入也可以使用本地 YAML、Python 实现等方式。

小练习：用“开关变更反向归因”回答三个问题：哪部分是排查步骤？哪几个操作是工具？其中哪些工具在实习里通过 MCP 提供？最后一题暂时想不起来，就记为待核对。

## 3 自己描述一个工具 25 分钟

前 10 分钟填下面四行，用中文即可。这是设计练习，不要求实现或接入仓库。

- 名称：`query_service_logs`
- 说明：查询指定命名空间和服务的最近日志，用于核对启动报错。
- 参数：`namespace` 和 `service` 为字符串；`limit` 为整数，建议默认 50，并在实现中限制最大值。
- 返回：日志内容与查询范围；失败时返回查询对象、参数以及底层错误。

然后回答：为什么需要 `limit`？如果服务不存在、日志为空或权限不足，各自应该返回什么信息？

参考：限制数量可以控制返回规模；“没有日志”应说明查了哪里、什么范围，“权限不足”应保留具体错误。Schema 是参数说明，实际实现仍须检查参数和权限，不能只凭模型填得像样就执行。

接下来 10 分钟，把一次调用串起来：

```text
模型看到工具说明
→ 返回工具名、参数和调用 ID
→ 程序找到工具实现并执行查询
→ 结果或错误关联同一个调用 ID，加入消息历史
→ 下一轮模型依据这些信息继续查询或给出回答
```

最后 5 分钟尝试用 30 秒讲完。无需背函数名；要说清“模型提出调用，程序执行，结果影响下一步”。

工具插件化的 90 秒参考回答：

> 排障要访问不同数据源，如果每增加一个数据源都修改 Agent 主循环，扩展和维护会很困难。可以把具体查询封装成工具，用统一的名称、说明和参数规范提供给模型，并由框架负责管理和调用。模型选择工具并给出参数后，程序按名称找到实现，执行查询，把结果关联调用 ID 后放回上下文。例如日志工具接收服务名、命名空间和数量限制；若查询失败，要带回明确的错误，供模型调整后续动作。这样主循环可以复用，不同工具负责各自的数据访问和业务检查。

合上文档再复述一次，换成你的说法。简历中的工具数量先不用背，优先把一个工具怎样接入和调用讲清楚。

## 4 用证据讲一次排障 20 分钟

下面根据仓库的 [09_crashpod 故障场景](../../tests/llm/fixtures/test_ask_holmes/09_crashpod/test_case.yaml) 改编为纸面练习。该 fixture 的服务会在缺少 `DEPLOY_ENV` 时退出；本次没有运行 Kubernetes 或模型评测。表中的证据用于练习推理，不能当作你本次实跑记录。

问题：“payment-processing-worker 为什么一直重启？”

| 已知观察 | 信息意味着什么 |
| --- | --- |
| 容器状态为 CrashLoopBackOff | 容器反复启动失败；这一状态本身不能确定根因 |
| 日志显示 `Environment variable DEPLOY_ENV is undefined` | 启动报错指向缺失的环境变量 |
| 配置核对没有提供 `DEPLOY_ENV` | 与日志形成交叉验证，可定位到启动配置缺失 |

先用 5 分钟写三句话：初步结论是什么、由哪两条证据支持、修复后还要验证什么。再用 5 分钟口述，最后 10 分钟对照以下参考与变式。

参考：启动配置缺少 `DEPLOY_ENV`，程序因此退出并被反复重启。依据是报错日志与配置检查。建议补齐该变量后观察容器能否稳定运行，并核对日志和服务功能；不能只看到 Pod Ready 就宣称故障已经解决。

变式：“查询日志时返回 permission denied。”你能直接说配置缺失吗？不能。应保留权限错误，说明当前缺少日志证据，尝试其他已授权的证据来源；仍不足时给出待确认结论，不能编造查询结果。

这一项学会的内容就是面试中的两句话：“状态是现象，结论需要证据”“工具失败需要作为信息返回，模型能否纠正还要看后续行为”。

## 5 面试口述 30 分钟

前 10 分钟录两段音：2 分钟项目介绍、90 秒工具插件化。允许先看提纲，第二遍再合上文档。每段最多重录两次，避免一直追求措辞。

后 20 分钟回答下面五题，每题约 2 分钟，其余时间只补一个最明显的卡点。

| 面试追问 | 回答至少包含什么 |
| --- | --- |
| 为什么要让 Agent 调工具？ | 模型需要访问当前环境的外部证据；工具执行结果回到下一轮 |
| 模型怎样知道该用哪个工具？ | 可见的名称、说明和参数规范，加上用户问题和已有观察；选择仍可能出错 |
| 新增工具要准备什么？ | 说明、参数、执行实现、返回与错误处理、接入配置；主循环负责统一调用 |
| 工具失败后怎么办？什么时候停止？ | 错误进入历史，可修正参数或换证据来源；正常完成、步数预算以及不可继续的错误等都要考虑 |
| 快手的 Skill 和这里的工具是什么关系？ | 用一个实际归因流程说明操作指导、工具能力、MCP 接入各自负责什么 |

第五题可参考：开关归因 Skill 给出排查方法，变更历史、灰度轨迹和堆栈查询等工具提供证据；MCP 可以提供统一接入方式。要进一步说出你参与哪部分、如何做证据交叉验证。

问到暂时不了解的实现时，准确说出已理解的机制，再指出待核对的部分。把问题写下来，每次只查一个具体位置。
