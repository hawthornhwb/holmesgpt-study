## 1 从接入需求理解为什么要插件化

教学场景：用户问“checkout-api 为什么一直重启？”调查可能要查询 Kubernetes 状态和事件、读取日志、查找相关知识。后续还希望加入一个“查询服务负责团队”的工具。

如果每接一个数据源都直接给调查主循环增加一段平台专用逻辑，主循环就要了解不同 API 的认证、参数、返回格式和错误处理。扩展数据源时，这些职责会一起增长。

插件化把职责分开：具体工具负责访问数据源；框架负责加载与管理工具、向模型提供描述、查找实现并统一调用。模型根据问题和已有证据提出工具调用请求。

用自己的话写 3 句：调查需要哪些外部能力？增加平台时会遇到什么维护问题？工具模块与框架分别承担什么工作？能回答这三句，就知道今天的设计在解决什么问题。

## 2 理解四个部分的职责

| 部分 | 负责什么 | 日志查询例子 |
| --- | --- | --- |
| **Tool** | 一个可执行的具体操作，具有名称、说明、参数和返回结果 | 查询指定服务的近期日志 |
| **Toolset** | 组织相关工具，管理共同配置、启用状态与前置条件 | 日志平台的查询工具共用连接配置 |
| **Schema** | 向模型描述工具名称、用途和参数规范 | 告诉模型填写服务、命名空间、时间范围和数量上限 |
| 执行实现 | 实际访问数据源，处理业务参数与底层错误 | 调用日志 API，或执行 YAML 定义的命令 |

这四项是职责划分。Schema 是工具对模型的描述，具体查询由执行实现完成。HolmesGPT 可以通过 YAML 命令工具、Python 工具等方式实现不同操作。

用中文描述一个教学工具即可：

```text
名称：query_service_logs（教学名称）
用途：查询指定服务的近期日志，用于检查启动报错。
参数：namespace、service、start、end、limit。
返回：日志及实际查询范围；查询失败时保留底层错误。
```

想一想：为什么说明里要写用途？为什么需要时间范围和 limit？为什么连接地址、认证等共同配置适合放在工具集这一层？

参考思路：说明帮助模型选择工具，参数让查询范围可控，共同配置方便统一管理。同一接口可以封装不同实现，但每个平台的业务含义与错误处理仍需具体实现。

## 3 用一个工具讲清接入 调用与失败

先看这条路径，再用日志工具复述：

```text
准备工具定义、执行实现和接入配置
→ 框架加载工具集，形成可用工具并按名称管理
→ 把名称、说明和参数 Schema 提供给模型
→ 模型返回工具名、参数与调用 ID
→ 程序查找工具，执行具体查询
→ 结果或错误关联调用 ID，进入后续调查
```

前半段解释“工具如何进入框架”，后半段解释“一个工具怎样被调用”。你已掌握后半段，今天重点补齐前半段的职责与理由。

再讨论三个情况：

- **模型给错参数。** Schema 帮助生成参数；执行前还需要参数处理和具体业务校验。**当前通用类型转换不是完整的 JSON Schema 校验**，具体工具仍需检查必填内容、范围等条件。可以保守转换的类型由通用转换处理，其余合法性由具体实现检查并返回错误。
- **查询权限不足。** 返回实际查询对象、参数、状态码与错误消息，供后续调查使用。模型能否纠正仍取决于已有权限、可用工具和后续行为。
- **查询没有日志。** 说明搜索的服务、命名空间和时间范围。没有查到日志本身不能证明服务正常或异常。

至少讲出两个取舍：统一接口降低接入成本，但不能消除平台差异；工具说明有助于选择，但提供大量工具 Schema 也占用上下文。工具数量多本身不能证明诊断质量高。

## 4 面试讲述与核心追问

先借助骨架讲一遍，再合上文档，用自己的话讲第二遍。参考段落介绍框架机制，个人工作在文末按实际经历填写。

> 故障调查需要访问 Kubernetes、日志平台等不同数据源，所以把具体查询封装成统一的工具模块。Tool 表示一个操作，Toolset 管理相关工具和共同配置；框架负责加载、管理和调用。工具通过名称、说明和参数 Schema 向模型描述能力，模型提出调用后，程序按名称找到实现并执行。例如日志工具接收服务、命名空间、时间范围和数量限制，具体实现负责查询以及业务参数检查，结果和底层错误交回后续调查。增加数据源时主要扩展工具及其接入配置，可以复用调查循环；同时还要考虑平台差异、工具选择错误和工具描述占用的上下文。

每个追问先回答 30–60 秒，卡住后只补当前问题。

| 核心追问 | 回答需要包含什么 |
| --- | --- |
| 为什么需要工具插件化？ | 多数据源接入需求；框架与数据访问职责分开；扩展时复用调查逻辑 |
| Tool、Toolset、Schema 分别负责什么？ | 一个操作、一组工具及共同管理、面向模型的能力描述 |
| 新增日志查询工具要准备什么？ | 名称与用途、参数、执行实现、配置与前置条件、结果和错误处理、验证 |
| 模型怎么知道用哪个工具，程序怎么找到实现？ | 模型依据描述和上下文选择；程序按名称查找；调用 ID 关联结果 |
| 参数错误、无数据、权限不足分别怎么办？ | 参数处理与业务校验；无数据说明查询范围；底层错误提供给后续调查 |

答顺以后，再补两个深入问题：为什么统一接口仍需要各工具做业务校验？工具多了会带来哪些选择和上下文成本？

简历里的“约 50 个工具集、250 个工具能力”涉及版本和统计口径。先讲清设计，数字以实际核对为准；可用工具还受启用配置与前置条件影响。

下面是查阅索引。每次选一个问题，最多查看两段相关代码；10 分钟后仍卡住，就保留问题，通过中文解释或具体输入输出继续学习。

| 当前疑问 | 查哪一小段 | 查到什么即可停止 |
| --- | --- | --- |
| 工具定义长什么样？ | [docker.yaml](../../holmes/plugins/toolsets/docker.yaml) 的 docker_inspect | 找到名称、用途和 command |
| 模型能看到具体 command 吗？ | [tools.py](../../holmes/core/tools.py) 的 get_openai_format() | 确认提供名称、说明和参数，command 与 user_description 不在这里传入 |
| 程序怎样按名称找到工具？ | [tool_executor.py](../../holmes/core/tools_utils/tool_executor.py) 的 get_tool_by_name() | 看懂工具名如何找到对象 |
| 通用调用与具体操作怎样分工？ | tools.py 的 invoke() | 看懂它调用 _invoke()，并处理通用调用流程 |

参数转换细节属于深入查证：**定义对象的 Pydantic 校验、模型参数 Schema、保守类型转换、具体业务校验是不同层次。** 当前转换路径中，缺失字段会跳过，未知字段保留，enum、范围与嵌套结构没有在这一步统一校验。原先强调的这些边界继续保留，但今天无需逐行研究转换函数。

如果一个问题确实需要实验支撑，可选择 [本地工具接入实验](tool-lab.md) 的离线部分，或阅读现有 [Schema 测试](../../tests/test_openai_formatting.py) 的一条相关断言。实验结果记录在本页，是否运行由当前疑问决定。
