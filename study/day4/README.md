# Day 4 分层上下文控制的设计与面试回答

2026-10-06 调整。对应 10-04 版简历中“智能故障诊断 Agent”的第二条：分层上下文控制。状态：计划已更新，学习与口述待你完成。

你已经理解工具结果会进入后续模型请求。今天围绕一个问题学习：**日志和 Kubernetes 数据很多，调查历史也不断累积，怎样控制上下文并保留下一步需要的证据？**

## 1 先看三种不同的问题

沿用 Day 3 的教学场景：“checkout-api 为什么一直重启？”以下数据用于设计推演，未表示本次真实运行结果。

| 遇到的情况 | 问题在哪里 | 优先怎么处理 |
| --- | --- | --- |
| 查出整个集群一天的日志，但只调查一个服务最近 15 分钟 | 查询范围太宽，大量数据与当前问题无关 | 尽早按对象、时间和数量收窄查询 |
| 范围已经合理，一次结果仍有大量日志或 JSON | 单条工具结果占用太大 | 在结果进入历史前单独处理 |
| 每次结果都能容纳，但多轮调查后历史很长 | 对话累计占用超过预算 | 下一轮请求前检查整体预算，必要时压缩历史 |

先解释这三种问题。区分它们以后，就能回答为什么需要分层：它们发生在不同位置，仅处理其中一层不能解决全部问题。

## 2 把分层方案讲成一条路径

```text
按对象、时间范围、数量等条件收窄查询
→ 数据源查询与必要的本地过滤
→ 控制单次工具结果的大小
→ 结果加入对话历史
→ 下一轮请求前核对整体 token 预算，必要时 Compaction
→ 模型继续调查
```

**查询阶段。** 尽可能把筛选交给支持这些参数的 API，减少传输量和无关信息；只能在本地筛选时，仍要控制返回规模。服务端过滤和本地 jq 过滤需要分开说明。当前 Loki 工具会把 query、start、end、limit 传给 API；kubernetes_jq_query 则分页获取数据后在本地做 jq 过滤。分页控制一页大小，遍历全部页并不保证最终结果少。

**单次结果阶段。** 对已经返回的一条结果做处理：可以配置 Transformer 摘要，或者使用当前仓库优先采用的大结果落盘机制。这个阶段只控制单次结果。

**整体历史阶段。** 每轮请求前检查历史与工具 Schema 的 token 占用，同时预留模型输出预算。接近配置的阈值时做 Compaction，把已有调查整理成较短的历史，再核对是否足以发送请求。

用“处理对象、发生位置、解决的问题”这三项解释每层即可，先不背阈值和函数名。

## 3 摘要 落盘与证据保留怎样取舍

你的简历提到 Transformer 摘要。当前仓库将 llm_summarize 标为历史机制，默认关闭且不推荐，仍为旧配置保留；大结果优先落盘。因此需要分别讲清“简历描述的摘要方案”和“当前实现采用的方案”，是否实际启用摘要以配置与运行记录为准。

| 机制 | 进入上下文的内容 | 主要价值 | 主要代价或限制 |
| --- | --- | --- | --- |
| Transformer 摘要 | 单次结果的摘要 | 减少单条输出的长度 | 增加模型调用成本和延迟，有损；被替换的原文不会由摘要自动恢复 |
| 单次结果落盘 | 文件路径、预览和读取提示 | 保存收到的结果，允许按需读取 | 依赖存储、文件访问能力和文件生命周期；读取也会占用调用和上下文 |
| 历史 Compaction | 既有调查的简短历史 | 控制多轮累计占用，保留调查进展 | 额外模型调用，有损；需要检查压缩效果与后续预算 |

落盘保留的是进入落盘阶段的结果。如果前面已经用 Transformer 摘要替换原文，后续落盘无法找回之前丢掉的内容。落盘也不能保证模型一定读取到关键证据。

**证据保留推演。** 假设教学日志是：“checkout-api 在 10:02 启动失败，报错 Environment variable DEPLOY_ENV is undefined”。摘要只写成“服务启动异常”，下一轮就失去了具体错误信息。

一份能支持继续调查的记录至少应保留：资源名与命名空间、时间范围、错误原文、查询条件、已验证的结论、已排除的假设、尚未确认的问题与下一步。压缩提示要求保留这些内容，但提示本身不能保证摘要无损；缺失时应重新读取仍可访问的原数据，或重新查询。

再推演三个失败分支：

- **单次结果超限且不能落盘：** 当前机制返回要求收窄查询的错误，后续需要调整查询。
- **Transformer 摘要报错或没有变短：** 工具处理层保留转换前内容；单次结果仍大时还需要后续大小控制。
- **Compaction 没有把历史压到可用预算：** 继续做硬上限检查；仍超限时会报错，不能因为“已经摘要过”就继续发超限请求。

## 4 面试讲述与核心追问

先借助骨架讲一遍，再合上文档讲第二遍。用自己的话说明各层的设计理由，方案与实测记录分别说明。

> 排障时既可能出现一次查询结果很大，也可能出现多轮调查历史累积过长，所以需要分层控制。查询阶段尽量按资源、时间和数量收窄范围，减少无关数据；单次结果在进入历史前控制大小，摘要能减量，但会有信息损失和额外成本。当前仓库优先把大结果落盘，在上下文中放路径、预览和读取提示，便于按需取回数据。下一轮请求前再核对历史、工具 Schema 和输出预算，必要时做 Compaction。历史摘要应保留具体资源、时间、错误和调查进展，缺失证据时重新读取或查询；处理结束还要检查是否符合整体预算。

每个追问先回答 30–60 秒，卡住后只补当前问题。

| 核心追问 | 回答需要包含什么 |
| --- | --- |
| 为什么需要分层，不能只做 Compaction？ | 无关数据、单条过大、历史累计是不同问题；尽早减量降低后续压力 |
| 单次结果摘要与历史 Compaction 有什么区别？ | 处理对象、触发位置和保留的信息不同 |
| 为什么当前仓库优先落盘？ | 摘要有损且增加成本；落盘保留收到的数据，可按需读，但有访问条件 |
| 压缩丢掉错误码或关键日志后怎么办？ | 核对证据；重新读取或查询；证据不足时保留待确认结论 |
| 为什么预算要包含工具 Schema，并预留输出？ | 模型请求不仅有历史文本；输入加输出必须符合上下文窗口 |

答顺以后，再补两个深入问题：分页和 limit 能保证总结果不大吗？摘要失败或压缩后仍超限，系统怎样处理？

可选的预算推演：假设窗口 10,000 tokens，历史 7,500、工具 Schema 1,000、输出预算 2,000，总计 10,500，超过窗口；需要减小占用并重新检查。数字是教学假设，具体触发阈值和输出预算以实际模型配置为准。

每次选一个问题，最多查看两段相关资料。10 分钟后仍卡住，就记录问题，通过中文解释或具体输入输出继续学习。

| 当前疑问 | 查哪一小段 | 查到什么即可停止 |
| --- | --- | --- |
| 两种上下文机制怎样配合？ | [上下文管理说明](../../docs/reference/context-management.md) 的前两节 | 确认单次结果和整体历史的处理位置 |
| 摘要现在默认启用吗？ | [llm_summarize.py](../../holmes/core/transformers/llm_summarize.py) 文件开头 | 确认历史机制与默认状态 |
| 落盘成功和失败时给模型什么？ | [tool_context_window_limiter.py](../../holmes/core/tools_utils/tool_context_window_limiter.py) 的 spill_oversized_tool_result() | 找到路径与预览，以及不能保存时的错误分支 |
| Compaction 为什么还要检查预算？ | [input_context_window_limiter.py](../../holmes/core/truncation/input_context_window_limiter.py) 的 compact_if_necessary() | 找到输入、工具 Schema 与输出预算，以及压缩后的上限检查 |

证据练习可直接用教学日志，也可从 [已有 Trace](../day1/runs/20260923-225409-379209/walkthrough.md) 选择熟悉的输出，手写摘要后比较遗漏。手工推演用于检查理解，不代表真实摘要模型的效果；Trace 未触发压缩时也不能据此宣称压缩效果已经验证。

需要实验核对失败分支时，再选择现有 [单次结果测试](../../tests/core/tools_utils/test_tool_context_window_limiter.py) 或 [历史压缩测试](../../tests/core/truncation/test_compaction.py) 的一条相关断言。旧计划编写时的验证记录为摘要 4 passed、单次结果 4 passed、历史压缩 2 passed；本次只调整学习文档，该记录不表示你的学习任务已完成，也不表示本次重新运行了测试。
