## 1 先看三种不同的问题

主案例仍是 `app-09` 的 `payment-processing-worker`，启动日志的关键证据是 `Environment variable DEPLOY_ENV is undefined`。原 fixture 没有制造大日志，也没有强制 Compaction；以下只扩大同一调查的数据规模，推演各层设计，本次未运行这些变化。

| 遇到的情况 | 问题在哪里 | 优先怎么处理 |
| --- | --- | --- |
| 发现 Pod 时返回全体资源的完整 JSON，只需要目标服务的状态 | 无关对象和字段占用太多 | 筛选目标资源，投影 namespace、Pod 名与容器状态 |
| 查准确 Pod 的日志，输出很多，启动错误在较早位置 | 单条工具结果占用太大 | 核对过滤、limit 和截断提示，再考虑后续大小控制 |
| 反复查状态、日志与配置，每次都能容纳，累计历史很长 | 对话累计占用超过预算 | 下一轮请求前检查整体预算，必要时压缩历史 |

先解释这三种问题。区分它们以后，就能回答为什么需要分层：它们发生在不同位置，仅处理其中一层不能解决全部问题。

## 2 把分层方案讲成一条路径

```text
按对象、时间范围、数量等条件收窄查询
→ 数据源查询与必要的本地过滤
→ 具体工具的数量限制或内部截断
→ 控制单次工具结果的大小
→ 结果加入对话历史
→ 下一轮请求前核对整体 token 预算，必要时 Compaction
→ 模型继续调查
```

**查询阶段。** 本例用 `kubernetes_jq_query` 发现 Pod 时，可以只返回匹配服务的名称与状态；当前实现分页读取 Kubernetes API，在本地做 jq 过滤。这样减少模型输入，不能宣称已减少 API 读取。`fetch_pod_logs` 当前也先读取当前和上一次容器日志，再本地做时间、包含/排除过滤与 limit。支持服务端条件的 API 应尽早筛选；讲方案时说明实际过滤位置。分页控制一页大小，遍历全部页不保证最终结果少。

**单次结果阶段。** 本例的 `PodLoggingTool` 内部先按 token 预算截掉较早日志。通用 `Tool.invoke()` 还会运行满足配置条件的 Transformer，后续再进入通用大小检查；过大的返回结果按条件落盘。这里需要区分具体工具的截断与框架的通用处理。

**整体历史阶段。** 每轮请求前检查历史与工具 Schema 的 token 占用，同时预留模型输出预算。接近配置的阈值时做 Compaction，把已有调查整理成较短的历史，再核对是否足以发送请求。

用“处理对象、发生位置、解决的问题”这三项解释每层即可，先不背阈值和函数名。

## 3 摘要 落盘与证据保留怎样取舍

你的简历提到 Transformer 摘要。当前仓库将 llm_summarize 标为历史机制，默认关闭且不推荐，仍为旧配置保留；大结果优先落盘。因此需要分别讲清“简历描述的摘要方案”和“当前实现采用的方案”，是否实际启用摘要以配置与运行记录为准。

| 机制 | 进入上下文的内容 | 主要价值 | 主要代价或限制 |
| --- | --- | --- | --- |
| Transformer 摘要 | 单次结果的摘要 | 减少单条输出的长度 | 增加模型调用成本和延迟，有损；被替换的原文不会由摘要自动恢复 |
| 单次结果落盘 | 文件路径、预览和读取提示 | 保存收到的结果，允许按需读取 | 依赖存储、文件访问能力和文件生命周期；读取也会占用调用和上下文 |
| 历史 Compaction | 既有调查的简短历史 | 控制多轮累计占用，保留调查进展 | 额外模型调用，有损；需要检查压缩效果与后续预算 |

落盘保留的是进入落盘阶段的结果。如果日志工具已过滤、limit 或截断掉较早内容，或 Transformer 已用摘要替换原文，后续落盘无法找回之前丢掉的内容。落盘也不能保证模型一定读取到关键证据。

**沿案例推演两个失败。** 第一种：大量日志的较早位置有 `Environment variable DEPLOY_ENV is undefined`，只返回最近 100 条或截断较早内容后，模型看不到它。第二种：摘要只写“payment-processing-worker 启动异常”，下一轮丢失具体变量名。两种情况都无法仅凭现象得出本例根因。

一份支持继续调查的记录应保留：`app-09`、准确 Pod 名、实际时间范围、错误原文、查询与截断条件、配置核对结果，以及尚未确认的事项。可以手写“日志报告变量为空，Deployment 未提供 DEPLOY_ENV，待按应用要求确认正确值”。压缩提示不能保证无损；缺失时重新读取仍可访问的数据，或重新查询。已经在工具内丢掉的日志要回数据源查询，不能仅回读后续落盘文件。

再推演三个失败分支：

- **单次结果超限且不能落盘：** 当前机制返回要求收窄查询的错误，后续需要调整查询。
- **Transformer 摘要报错或没有变短：** 工具处理层保留转换前内容；单次结果仍大时还需要后续大小控制。
- **Compaction 没有把历史压到可用预算：** 继续做硬上限检查；仍超限时会报错，不能因为“已经摘要过”就继续发超限请求。

## 4 面试讲述与核心追问

先借助骨架讲一遍，再合上文档讲第二遍。用自己的话说明各层的设计理由，方案与实测记录分别说明。

> 在支付服务重启的 case 中，要保留 DEPLOY_ENV 的具体错误和配置核对结果。查询资源时先筛选对象与字段，日志按准确 Pod、时间和过滤条件减量；我会区分服务端与本地过滤。单次结果还可能在工具内部截断，或经过摘要与通用落盘。当前仓库默认关闭旧摘要机制，通用大结果优先落盘，但保存的是已处理结果，不能恢复之前截掉的日志。多轮历史则在下一次请求前连同工具 Schema 和输出预算一起检查，必要时 Compaction。各层都需要关注证据保留，不能只剩“启动异常”；缺失时根据丢失位置回读数据或重新查询。

每个追问先回答 30–60 秒，卡住后只补当前问题。

| 核心追问 | 回答需要包含什么 |
| --- | --- |
| 为什么需要分层，不能只做 Compaction？ | 无关数据、单条过大、历史累计是不同问题；尽早减量降低后续压力 |
| 单次结果摘要与历史 Compaction 有什么区别？ | 处理对象、触发位置和保留的信息不同 |
| 为什么当前仓库优先落盘？ | 摘要有损且增加成本；落盘保留收到的数据，可按需读，但有访问条件 |
| DEPLOY_ENV 日志在工具内被截掉，落盘能找回来吗？ | 落盘收到的是已处理结果；回数据源查询，核对范围与过滤；避免无证据断言 |
| 为什么预算要包含工具 Schema，并预留输出？ | 模型请求不仅有历史文本；输入加输出必须符合上下文窗口 |

答顺以后，再补两个深入问题：分页和 limit 能保证总结果不大吗？摘要失败或压缩后仍超限，系统怎样处理？

可选的预算推演：假设窗口 10,000 tokens，历史 7,500、工具 Schema 1,000、输出预算 2,000，总计 10,500，超过窗口；需要减小占用并重新检查。数字是教学假设，具体触发阈值和输出预算以实际模型配置为准。

| 当前疑问 | 查哪一小段 | 查到什么即可停止 |

| 本例日志在哪里过滤或截断？ | [kubernetes_logs.py](../../holmes/plugins/toolsets/kubernetes_logs.py) 的 filter_logs()；[logging_api.py](../../holmes/plugins/toolsets/logging_utils/logging_api.py) 的 truncate_logs() | 本地过滤、limit 取较晚内容、按 token 预算截断早期内容 |
| 两种上下文机制怎样配合？ | [上下文管理说明](../../docs/reference/context-management.md) 的前两节 | 确认单次结果和整体历史的处理位置 |
| 摘要现在默认启用吗？ | [llm_summarize.py](../../holmes/core/transformers/llm_summarize.py) 文件开头 | 确认历史机制与默认状态 |

证据练习直接用这个 case 的错误原文和 Deployment 配置：先手写一份支持下一步的短记录，再故意删掉变量名，说明结论会受到什么影响。手工推演不代表摘要模型效果；[已有 Trace](../day1/runs/20260923-225409-379209/walkthrough.md) 也不是这个 Kubernetes case 的运行记录。

需要实验核对失败分支时，再选择现有 [单次结果测试](../../tests/core/tools_utils/test_tool_context_window_limiter.py) 或 [历史压缩测试](../../tests/core/truncation/test_compaction.py) 的一条相关断言。旧计划编写时的验证记录为摘要 4 passed、单次结果 4 passed、历史压缩 2 passed；本次只调整学习文档，该记录不表示你的学习任务已完成，也不表示本次重新运行了测试。
