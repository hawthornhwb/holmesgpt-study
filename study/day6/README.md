## 1 从一个可复现故障理解评估目标

参考仓库的 [09_crashpod 场景](../../tests/llm/fixtures/test_ask_holmes/09_crashpod/test_case.yaml)：payment-processing-worker 缺少 DEPLOY_ENV 环境变量，启动脚本输出对应错误并退出，容器反复重启。用户只问这个服务有什么问题，expected_output 要求指出该变量未定义或缺失。

前三天使用的仍是这一个场景，本页把同一次调查接回测试入口。本次没有启动集群或运行模型评测。

先判断三种教学回答：

| 回答 | 能说明什么 | 还缺少什么 |
| --- | --- | --- |
| “服务处于 CrashLoopBackOff” | 描述了现象 | 没有指出具体根因 |
| “可能是环境配置问题” | 提出了一个宽泛假设 | 缺少具体配置项与证据 |
| “DEPLOY_ENV 缺失，启动报错后退出” | 匹配这个场景的具体根因 | 还需结合实际工具记录核对证据来源 |

评估先定义需要检查的结论，再决定怎样检查。回答流畅、篇幅长或调用很多工具，都不能单独证明根因正确。

## 2 理解评估流程与检查方式

```text
构造或复用可重复的故障场景，确认故障实际存在
→ 给 Agent 用户问题与允许访问的数据源
→ 保存回答、工具调用、时间与用量记录
→ 用规则检查确定性条件，用 LLM Judge 判断预期内容是否匹配
→ 汇总通过情况和效率指标
→ 查看失败 Trace，区分调查失败、评审问题与环境问题
```

场景至少包含问题、已知根因、可查询证据、预期答案和环境准备方式。根因应来自故障构造或人工确认；环境准备失败要单独记录，不能把它误当作 Agent 的诊断能力问题。

先把这个 case 的字段和职责对上：

| 实际字段或步骤 | 本例具体内容 | 为什么需要 |
| --- | --- | --- |
| before_test | 创建缺少 DEPLOY_ENV 的 Deployment，等待 Pod 出现及 CrashLoopBackOff | 让预期根因有可重复查询的环境证据 |
| user_prompt | 只问 payment-processing-worker 有什么问题 | 让 Agent 自己发现 namespace、Pod、错误和配置 |
| expected_output | 指出 DEPLOY_ENV 未定义或缺失 | 给 Judge 一个明确的语义目标 |
| memories_generated: false | 不应产生 Skills 建议 | 用确定性行为要求约束这次常规调查 |
| after_test | 删除测试命名空间 | 管理测试环境；不属于 Agent 执行的修复 |

结合前面三天形成的教学路径，查看记录时应能回答：模型通过什么查询找到了 Pod？哪次返回包含具体错误？是否核对了配置？失败或截断发生在哪里？原 case 未强制这些调用顺序，检查重点是证据能否支持答案。

**规则断言**适合程序可以明确判断的条件，例如是否调用禁止的工具、Token 是否超配置上限、具体字段或工具记录是否符合要求。**LLM Judge**适合判断不同措辞是否表达了预期根因，以及是否满足明确的语义要求。

当前 correctness Judge 根据 expected_output 判断内容是否匹配；默认 strict 类型要求所有预期要点都满足，并给出 1 / 0 分。评审输入默认还可能包含中间 assistant 输出，分析分数时也要核对最终答案。该 case 的 memories_generated: false 会检查建议数量；test_ask_holmes.py 的禁止工具和 Token 上限断言则需要相应字段，本 case 未配置这些要求。

有两个实现细节需要说准确：

- **expected_output 用于评估，Agent 不会看到这份答案要求。** 用户问题应让它自行调查，不能把根因或验证值提前写进提示。
- **include_tool_calls: true 会把工具调用信息提供给 Judge，属于评审输入。** 本 case 没有设置这一项，它也不是“必须调用某工具”的硬断言。若需要确定性验证证据获取，应直接检查实际调用记录。

Judge 可能误判，规则也可能过窄。固定清楚的要求，人工复核有争议的结果，再调整标准，才能让分数更有解释力。

## 3 指标 怎样防止猜中与公平比较

| 指标 | 回答什么问题 | 需要说明的口径 |
| --- | --- | --- |
| 通过率 | 场景要求满足了多少次？ | 通过次数 / 有效运行次数；说明场景数、重复次数和排除项 |
| 调查耗时 | 用户要等多久？ | 明确起止位置；区分 Agent 调查、环境准备和 Judge 评审时间 |
| 模型调用次数 | 调查用了多少次模型交互？ | 与工具调用次数分别统计 |
| 工具调用次数 | 查询工作量和重复操作有多少？ | 结合 Trace 判断必要查询与无效重复 |
| Token 消耗 | 请求消耗多少模型用量？ | 明确输入、输出、缓存与压缩调用的统计范围 |
| 费用 | 这次诊断用了多少成本？ | 说明包含的调用；Judge 与环境成本是否另计 |

当前 harness 的 holmes_duration 计时包围 ai.call()，Judge 在后续评估阶段执行；报告记录模型与工具调用数、Token 和费用。结果统计中的有效运行次数排除 skipped、setup failure 和 throttled 项。通过率是给定场景集与标准下的通过情况，不能直接推断为所有线上故障的准确率。

**防止猜中。** 如果 expected_output 只要求“存在配置问题”，模型可能凭经验满足要求。更强的设计检查可通过查询才能发现的具体配置项、错误码、资源标识或验证值，再核对证据来源。09_crashpod 的具体变量名比泛泛的“配置异常”更有区分力，但这不等于仅凭这个案例就完全排除猜测。

针对同一个 case 可以提出的改进是：核对实际返回是否包含该变量的日志或配置证据，检查最终结论是否引用相符资源，并在不同故障实例中改变待发现的配置项。这里是评估设计练习，尚未修改测试；不把固定某个工具或固定调用顺序当成唯一正确路径，因为读取配置也可能发现根因。

**比较两个方案。** 以下数字全部是教学假设，未表示实测结果或当前模型价格：

| 方案 | 通过次数 / 有效运行次数 | 平均调查耗时 | 平均模型调用次数 | 平均费用 |
| --- | --- | --- | --- | --- |
| A | 8 / 10 | 40 秒 | 6 次 | 0.02 美元 |
| B | 9 / 10 | 65 秒 | 8 次 | 0.04 美元 |

先说清 B 的通过率更高，同时耗时与费用增加，再结合使用目标判断是否值得；10 次运行样本很少，应查看失败类型并重复验证。比较时保持相同场景、工具权限、评价标准与调用预算，记录模型和配置变化。Judge 模型或提示变化也会影响可比性。

失败分析可以按四类讲：数据没有查到、证据已经查到但推理错误、预算或调用过程失败、评审标准或 Judge 存在问题。先看一条具体 Trace，再讨论总体通过率，避免平均值掩盖原因。

## 4 面试讲述与核心追问

先借助骨架讲一遍，再合上文档，用自己的话讲第二遍。个人实际跑过的场景与结果填写在文末；当前没有实测数字时，讲清评估设计和核对依据。

> 在 09_crashpod 中，测试先创建缺少 DEPLOY_ENV 的支付服务并确认故障，再让 Agent 只根据服务名调查。Judge 检查是否表达了具体变量缺失，规则另外约束不产生 Skills 建议。这个语义分数能检查根因内容，但不自动保证答案来自查询，所以还应看实际日志或配置证据；本 case 没有强制某种工具顺序。效率记录 Agent 调查耗时、模型与工具调用次数、Token 和费用，Judge 与环境准备的口径分开。比较改动前后时固定场景、权限和标准，重复运行，再分析失败是没查到数据、丢失证据、推理错误还是评审问题。

每个追问先回答 30–60 秒，卡住后只补当前问题。

| 核心追问 | 回答需要包含什么 |
| --- | --- |
| 怎样构造故障场景，正确答案从哪里来？ | 已知根因、真实可查询证据、环境验证；答案用于评价而不提前交给 Agent |
| 为什么同时使用规则断言和 LLM Judge？ | 确定性条件与语义匹配的分工；各自的局限和争议复核 |
| 怎样判断答案来自调查，避免猜中？ | 具体可发现信息、实际工具证据；include_tool_calls 与硬断言的区别 |
| 通过率和耗时、调用次数、Token、费用怎样一起看？ | 质量与效率一起比较；明确分母、计时和成本范围 |
| 怎样比较两个方案，失败或 Judge 误判后怎么办？ | 固定场景与评估条件、重复运行；查看 Trace、分类问题、人工复核 |

答顺以后，再补两个深入问题：单元测试通过为何不能证明模型诊断正确？一次评测通过为何不足以说明结果稳定？

## 5 遇到具体疑问时怎样查证

每次选一个问题，最多查看两段相关资料。10 分钟后仍卡住，就记录问题，通过中文解释或输入输出推演继续学习。

| 当前疑问 | 查哪一小段 | 查到什么即可停止 |
| --- | --- | --- |
| 场景与预期根因在哪里定义？ | [09_crashpod](../../tests/llm/fixtures/test_ask_holmes/09_crashpod/test_case.yaml) 的 user_prompt、expected_output 和启动脚本 | 区分用户看到的问题与评估用的答案 |
| Judge 根据什么评分？ | [classifiers.py](../../tests/llm/utils/classifiers.py) 的 evaluate_correctness() | 找到 expected 要点、strict 标准和 1 / 0 分 |
| 工具记录与规则断言怎样参与评估？ | [property_manager.py](../../tests/llm/utils/property_manager.py) 的 include_tool_calls 分支；[test_ask_holmes.py](../../tests/llm/test_ask_holmes.py) 的 forbidden_tools 与 max_tokens 断言 | 区分交给 Judge 的信息与程序直接判定的条件 |
| 耗时与通过率的口径是什么？ | test_ask_holmes.py 中 ai.call() 的计时；[terminal_reporter.py](../../tests/llm/utils/reporting/terminal_reporter.py) 的 count_results() | 确认计时边界与有效运行分母 |

核心学习可以用场景定义、教学回答与假设指标完成。如果已有真实结果，可选一条 Trace 核对根因、证据、耗时和用量；方案、已有实测、本次纸面推演分别记录。需要创建或运行新 eval 时，再按仓库的 create-eval 流程处理环境与验证。
